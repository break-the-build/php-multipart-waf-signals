# Public PoC review and coverage expansion — 2026-10-21

Scope: static inspection of public research repositories and public X material, plus our own synthetic, offline detection demonstration. No third-party PoC code was executed, no public target was probed, and no exploit success is inferred from an HTTP error or a session-progress value. The three new GitHub checkouts were fetched for static inspection with user approval and pinned below. Complete untrusted checkouts are archived locally in the companion research workspace; do not execute them as part of this rule pack.

## Evidence standard

The [PHP CVE-2026-109618 advisory](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w) describes OOM `longjmp` corruption; the [CVE-2026-109619 advisory](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp) describes stale state across request boundaries. A repository title, callback reachability, HTTP 5xx, timeout, or an observed progress session value does not establish a use-after-free. A stock vulnerable build needs a sanitizer invalid-access trace or equivalent primary evidence, with a same-input fixed-build control, for a local CVE reproduction claim.

## Coverage map against published mechanisms

| Published area | Current observation | Uncovered requirement |
|---|---|---|
| CVE-2026-109618 multipart OOM: no usable declared length, many part headers, nested names, empty file controls | R7 (ModSecurity/njs), R5 (Suricata header inflation; ModSecurity nested names); all observational. | Empty-file metadata amplification has no reliable active rule. Bound multipart part/header counts and decoded size at the frontend; R5/R7 need engine replay. Non-multipart, application-specific OOM is outside request-shape coverage. |
| Upload-progress session/decoder lifecycle and memory disclosure | R1 body session name, new R8 cookie session name, R3 size heuristic, redacted cookie-anomaly and same-worker review. | Neither rule can prove an interrupted producer, reused worker, reclaimed memory or disclosure. A configured session/progress name can differ from defaults. |
| CVE-2026-109619 fatal backtrace plus early INI diagnostic | Offline triage now correlates a trusted origin fatal-error flag or late-cleanup diagnostic with a later pre-init INI diagnostic on the same PHP worker. | No general edge-only request signature. A diagnostic can occur without a log entry; instrument phase and worker identity at the origin. |
| OPcache cross-worker type confusion and other conditional state | None in the WAF rules. | A per-worker sequence heuristic cannot see the shared-state interaction. Use patch status, PHP/OPcache telemetry and incident response evidence. |

The [Wiz technical writeup](https://www.wiz.io/blog/php2shell-php-rce) separates upload-progress unserializer, memory disclosure, fatal backtrace and OPcache cases. The PHP advisories cover broader classes. Do not infer that one multipart rule covers all of them.

## Our benign proof of detection

A separate 690-byte, synthetic cookie-plus-progress-field form was sent to the already built PHP 8.4.26 and 8.4.27 CGI binaries inside a `--network none` container. Both returned the same parsed cookie, progress field and file metadata; no ASan invalid access was reported. The transcript is in `artifacts/public-poc-review-2026-10-21/php-waf-poc-review-php-cgi.stdout`. This confirms a real request shape on both sides of the PHP fix, and demonstrates why an R8 hit alone cannot identify a vulnerable version.

Run `python3 scripts/benign_detection_poc.py` locally. It imports only this repository's code, makes **no network connection**, and uses synthetic requests/events. It shows an ordinary upload classified clean, a progress-plus-body-session request shape, a progress-plus-session-cookie request shape, and a same-worker non-multipart fatal/diagnostic sequence prioritized for review while a different worker does not correlate. Its output is retained in the verification log. These observations show rule and triage behavior; they are **not a vulnerability PoC** or evidence that either CVE was triggered.

R8 is log-only. It must be scoped to PHP upload routes, tuned to the actual configured session and progress names, and replayed against ordinary application uploads before operational use. The current ModSecurity and njs implementations have passed structural/mock tests, not actual engine validation. Public PoC code was not run, so no claim is made that any of the three newly inspected exploit scripts works on stock PHP.
